# 安心圈 HavenCircle — 開發階段規劃

> 2026-07-15 建立。基於第一版產品構思 + 10 項功能缺口分析。
> 分階段原則：**先做完「不需要後端」的所有價值，把後端決策推遲到互動閉環驗證之後。**
>
> **進度（2026-07-15）**：階段 0、1、2、3 已完成。後端決策採 **CloudKit + CKShare**。
> 階段 3 的跨帳號流程需實機驗證，設定與測試邊界見 `CLOUDKIT_SETUP.md`。
> 剩餘：階段 4（接真實資料源與推播基礎設施）、階段 5（上線硬化）。

## 階段 0：地基重構（動新功能之前必做）

**為什麼先做**：現在 13 個型別擠在一個 129 行的檔案裡，每個 View 都是單行壓縮寫法。再往上疊 10 個功能，改動成本會指數上升。

- [ ] 拆檔：`Models/`（3 個 @Model）、`Views/`（每個畫面一檔）、`Services/`（通知、種子資料）
- [ ] 修現有隱患：
  - `try!` 建 ModelContainer、`URL(string:)!` 強制解包（違反「錯誤處理要明確」）
  - 「暫停提醒」只改了 UserDefaults 旗標，實際排程通知的路徑沒有檢查它 → 暫停是假的
  - `alertTypes` 用頓號字串儲存 → 改成可查詢的結構
- [ ] 建立 `xcodebuild` 驗證習慣（AGENTS.md 要求）
- 驗收：功能與現在完全相同，但每個 View 可獨立 preview，build 通過

## 階段 1：本機互動閉環（四個純本機功能）

**為什麼是這四個**：全部只靠 UserNotifications + SwiftData 就能完成，維持 AGENTS.md「自足、確定性、可 preview」的約束。

- [ ] **事件狀態機與解除通知**（缺口 #5）：事件加 `status`（進行中/持續確認中/已解除），狀態轉為已解除時發解除通知；「標記為已結束」走同一條路
- [ ] **時段感知生活圈**（缺口 #4）：LifeCircle 加每週作息時段（如「公司＝週一到五 08–19」），比對事件時間決定通知權重；時段外降為 App 內顯示
- [ ] **每日安全摘要**（缺口 #6）：UNCalendarNotificationTrigger 固定時間發「今天全家生活圈平安／過濾了 N 件低風險事件」；設定頁可調時間或關閉
- [ ] **演練模式**（缺口 #10）：現有 EventEditorView 改造成正式的「演練」入口——產生模擬事件 → 走完整通知流程 → 顯示每個通知權限狀態的檢查清單
- [ ] **資料時效標示**（缺口 #9 前半）：畫面顯示「資料更新於 X 分鐘前」，為離線降級鋪路
- 驗收：模擬器實跑每條流程，通知真的送達/解除；暫停提醒時演練事件不發通知

## 階段 2：資料層擴充（仍然免後端）

**為什麼這樣做**：用「內嵌開放資料 + 假資料管線」把後端該有的架構形狀先在本機建好，之後接真源只換資料來源，不動架構。

- [ ] **EventProvider 協定**：定義「來源擷取 → 分類 → 去重 → 可信度 → 生活圈比對」的本機管線介面，先用確定性的 mock provider 實作（preview 可跑）
- [ ] **全域災害層**（缺口 #3）：新增 `RegionAlert` 模型（按行政區，不是點+半徑），生活圈記錄所在行政區；地震/颱風警特報用 mock 資料驗證 UI 與匹配邏輯
- [x] **緊急資源地圖**（缺口 #8）：內嵌**全國**避難收容所（5,872 筆）/急救責任醫院（205 筆）開放資料為 bundle JSON（1.0 MB，2026-07-16 已從雙北擴為全國），地圖新增圖層開關；事件詳情頁加情境化快捷（火災→撥 119＋最近避難所導航）
- [ ] **事件歷史與趨勢**（缺口 #7）：過期事件不刪、改標 archived；新增「區域回顧」視圖（30 天事件統計），解決新使用者空地圖的冷啟動問題
- 驗收：斷網狀態下 App 全功能可用（因為全部本機）；行政區型警報能正確命中生活圈

## 階段 3：帳號與家庭連結（第一次需要後端）⚠️ 進場前有一個決策

**決策點（需要你選）**：
- **A. CloudKit + CKShare**：零後端伺服器、免費、符合「先用系統 API」慣例，家庭共享直接用 CKShare 邀請流程。代價：**鎖死 Apple 生態**，未來 Android/Web 版要重做。
- **B. Supabase/Firebase（照原構思）**：跨平台路線保留，但要開始養後端（帳號、資料表、推播服務、費用）。
- 我的建議：如果目標是先在雙北用 iOS 驗證產品，選 A 快很多；如果「之後出 Android/Web」是認真的承諾，直接選 B，避免遷移成本。

- [ ] 帳號系統與家人邀請（缺口 #1）：邀請連結/QR code → 對方接受 → 雙帳號綁定；被加入者可見自己被設了哪些生活圈、可退出
- [ ] **安否回報＋已讀**（缺口 #2）：「通知家人」變成真的跨裝置推播；收到方一鍵「我平安」回報全家；發起方看得到已讀/未讀
- [ ] 未安裝 App 家人的 fallback（簡訊分享連結）
- 驗收：兩台實機（或實機+模擬器）完整走一遍「事件 → 通知媽媽 → 媽媽回報平安 → 我看到」

## 階段 4：真實資料源與推播基礎設施

- [ ] 接真實來源：NCDR 災害示警（CAP 開放資料）、消防與警政開放資料、CWA 地震/颱風 API —— 逐源替換階段 2 的 mock provider
- [ ] 伺服器端管線：來源輪詢、去重、可信度評分、與使用者生活圈比對後派發推播（APNs）
- [ ] **完整離線降級**（缺口 #9 後半）：本機快取最後同步結果、斷網明確標示、高風險事件簡訊備援
- [ ] 通知限流與去重（同一事件不連續打擾）
- 驗收：真實資料連跑 7 天，人工抽查誤報率與延遲

## 階段 5：上線前硬化

- [ ] 隱私與法務：非緊急服務聲明、資料來源與限制告知、住址加密
- [ ] 監控：來源健康度、推播送達率、Sentry
- [ ] TestFlight 封測（雙北種子使用者），收集「提醒準確度」回饋
- 驗收：封測使用者的通知疲勞回報率、留存數據
