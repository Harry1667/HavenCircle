# 政府災害公開資料 — 接取指南與後端架構建議

> 2026-07-15 建立。用途：把 App 裡的 mock 假資料，換成真實的政府災害示警。
> 本文分三部分：**(一) 四個資料源怎麼拿**、**(二) 要不要一台伺服器（架構建議）**、**(三) App 端斷網降級與通知去重怎麼改**。
> 資料源接取方式已於 2026-07-15 實際上網查證；標「未完全確認」的項目請以官方頁面為準。

## 一、四個資料源：要什麼、去哪拿、怎麼拿

### 快速總覽

| 資料源 | 要不要申請 | 格式 | 給你什麼 | 對本 App 的角色 |
|---|---|---|---|---|
| **NCDR 民生示警平台** | ❌ 免申請直接抓 | CAP（XML）＋ JSON 索引 | 颱風、地震、淹水、土石流、**火災**、豪雨、停水、高溫等 43 項示警 | **主幹**：即時災害示警都從這裡來 |

### 1. NCDR 民生示警平台（★ 最重要，先接這個）

**這是什麼**：國家災害防救科技中心，把 28 個政府機關的 43 種災害示警，統一整理成國際標準格式（CAP）放在一個地方。你不用分別去對接氣象署、消防署、水利署——它全部幫你彙整好了。這就是為什麼建議先接它。

- **入口網站**：https://alerts.ncdr.nat.gov.tw/
- **開發者文件**：https://alerts.ncdr.nat.gov.tw/web/developer/cap-docs
- **要不要申請**：不用。沒有 API key，完全公開，直接用程式抓。
- **資料格式**：CAP（Common Alerting Protocol，一種國際通用的災害示警 XML 格式）。另外有一個 JSON 索引檔告訴你「現在有哪些示警正在生效」。

**怎麼拿（兩步驟）**：

第一步，抓「現在有效的示警清單」（這支會自動更新，你不用自己算哪些過期了）：

```bash
# 回傳目前生效中的所有示警，每筆都附一個 .cap 檔的下載連結
curl "https://alerts.ncdr.nat.gov.tw/JSONAtomFeeds.ashx"
```

第二步，從清單裡拿到每筆的 `.cap` 連結，逐一抓下來解析。實際的 CAP 檔網址長這樣（路徑裡的機關代碼會告訴你這是哪種災害）：

```
火災：    https://alerts.ncdr.nat.gov.tw/Capstorage/NFA/2026/NFA_Fire/[編號].cap
高溫：    https://alerts.ncdr.nat.gov.tw/Capstorage/CWA/2026/heatWave/[編號].cap
強風：    https://alerts.ncdr.nat.gov.tw/Capstorage/CWA/2026/Weather_warnings_WIND/[編號].cap
停水：    https://alerts.ncdr.nat.gov.tw/Capstorage/TWC/2026/TWC_water/[編號].cap
水庫放流：https://alerts.ncdr.nat.gov.tw/Capstorage/WRA/2026/ReservoirDis/[編號].cap
```

**涵蓋內容**：颱風、地震、淹水、土石流是明確包含的核心項目，另外還有火災、豪雨、強風、高溫、停水、水庫放流、行動電話中斷、傳染病等，總共 43 項。

**注意事項**：
- CAP 檔路徑裡有年份資料夾（`/2026/`），跨年時程式要記得換。
- 沒有明列呼叫次數限制（它是靜態檔直接抓），但**基於禮貌與穩定，建議你的伺服器每 1～5 分鐘抓一次索引就好，不要每秒狂打**。
- **未完全確認**：查證當下索引檔回傳的是 8 種正在生效的示警，完整 43 項的清單要看實際發布狀況，以 cap-docs 頁面的來源清單為準。

**CAP 檔裡有什麼**（解析時對應到 App 的欄位）：事件類型、發布機關、生效與失效時間、影響的地理範圍（有的是行政區、有的是經緯度多邊形）、嚴重程度、描述文字。這正好對得上 App 現在的 `LocalSafetyEvent` 與 `RegionAlert` 兩個模型。

### 2. CWA 中央氣象署開放資料平臺（要更精細的地震/颱風時再接）

**這是什麼**：氣象署自己的開放資料平台。NCDR 的地震颱風資料其實上游就是這裡，但如果你要「地震規模精確到小數點、颱風的完整路徑座標」這種細節，直接接 CWA 拿到的資料比較完整。

- **入口網站**：https://opendata.cwa.gov.tw/
- **開發手冊**：https://opendata.cwa.gov.tw/devManual/insrtuction
- **線上 API 文件**（可直接產生測試網址）：https://opendata.cwa.gov.tw/dist/opendata-swagger.html

**申請授權碼流程**（免費，你要自己做一次）：
1. 進網站右上角「登入/註冊」，用 email 或 Facebook 註冊氣象會員。
2. 收確認信、點連結啟用。
3. 登入後點「取得授權碼」，複製那串 API key（下面呼叫時會用到）。

**怎麼拿**（把 `{授權碼}` 換成你申請到的 key）：

```bash
# 通用格式
curl "https://opendata.cwa.gov.tw/api/v1/rest/datastore/{資料代碼}?Authorization={授權碼}&format=JSON"

# 範例：顯著有感地震報告
curl "https://opendata.cwa.gov.tw/api/v1/rest/datastore/E-A0015-001?Authorization={授權碼}&format=JSON"
```

**常用的資料代碼**：

| 資料 | 代碼（dataid） |
|---|---|
| 顯著有感地震報告 | `E-A0015-001` |
| 小區域有感地震報告 | `E-A0016-001` |
| 颱風警報（單一報） | `W-C0034-001` |
| 颱風侵襲機率 | `W-C0034-003` |
| 天氣特報／豪大雨特報（各縣市警特報現況） | `W-C0033-001` |

- **海嘯**的資料代碼**未完全確認**，在「地震海嘯」主題頁（https://opendata.cwa.gov.tw/dataset/earthquake ）或上面的 Swagger 文件可查到。
- **呼叫頻率限制未完全確認**：多篇教學提到一組授權碼一天約 1000 次上限，但官方文件沒明講數字，實際以登入後會員頁為準。對本 App 來說，伺服器每幾分鐘抓一次遠遠用不完。

### 3. 消防局即時火災 —— 此路不通，改走 NCDR

**誠實結論：台北市、新北市消防局都沒有提供「即時火災點位」的官方 API。** 查證結果：

- 台北市消防局有一個「119 即時案件資訊網」（https://service119.tfd.gov.tw/service119/accCase ），但那**只是給民眾看的網頁**，沒有開放 JSON/CSV/API 給程式抓。網路上有第三方自己爬取那個網頁的服務，但那不是官方、不穩定、也有法律風險，不建議依賴。
- 消防單位官方開放的都是**年度統計**（火災原因、損失統計年報表），不是即時的，對「馬上通知家人」沒用。

**所以火災怎麼辦**：就用第 1 項 NCDR 平台裡的 `NFA_Fire` 那條 feed。NFA 就是消防署（National Fire Agency），NCDR 已經幫你把消防署的火災示警整理成 CAP 了。你不用自己去對接消防局。

### 4. data.gov.tw 政府資料開放平臺（避難所等固定清單）

**這是什麼**：全國政府開放資料的總入口。對本 App 來說，這裡拿的是「不會即時變動」的東西——避難收容所、急救責任醫院清單（也就是 App 現在用內建 JSON 寫死的那些，之後可以改成從這裡定期更新）。

- **入口**：https://data.gov.tw/ ，搜尋頁 https://data.gov.tw/datasets/search
- **怎麼找**：搜關鍵字「避難收容所」「急救責任醫院」「消防」。
- **要不要申請**：多數資料集免 key，直接有 CSV/JSON 下載連結；少數會導到各縣市子平台，那些可能要該平台的 key。
- **避難收容所更完整的來源**：NCDR 也有一個資料服務平台（https://datahub.ncdr.nat.gov.tw/ ），收錄全國約 776 筆避難收容所，含地理資訊格式。

**建議**：這類靜態清單不用即時抓，你的伺服器一週更新一次、甚至手動半年更一次都行。優先度低於前面的即時示警。

## 二、要不要一台「隨時在線的伺服器」？

**先回答你的核心疑問**：你說「我寫一個網站去拿這些資料，App 再到網站上拿」——**這個想法方向完全正確，而且那個網站本身就是一台伺服器**（網站一定要跑在某台電腦上）。所以問題不是「要不要伺服器」，而是「這台伺服器要做多少事」。答案取決於一個關鍵區別：**App 是「自己去拉」還是「被動接收推播」。**

### 兩種模式的差別（這是整個架構的分水嶺）

**模式 A：拉（App 自己定時去問）**
- App 每隔幾分鐘主動去你的網站問「有沒有新事件」。
- 這種只需要一個很單純的中間層：定時抓政府資料 → 整理乾淨 → 放成一個 JSON 檔或簡單 API，等 App 來拿。
- **缺點很致命**：App 沒開的時候，它不會去拉，使用者就收不到警報。對一個「家人安全警報」App 來說，這等於廢了一半——家人出事，你要立刻震動知道，不是等你哪天想到打開 App 才看到。

**模式 B：推（伺服器主動把警報推到你手機）**
- 事件一發生，就算 App 關著、手機在口袋裡，也會震動跳通知。
- 這**一定**需要一台能主動發推播（APNs，Apple 的推播服務）的伺服器。這是 Apple 的硬性規定：推播只能從伺服器發，App 自己在關閉狀態下沒辦法叫自己跳通知。

**結論：這個 App 的核心價值就是模式 B。** 所以「要不要一台能主動做事的伺服器」——要。但好消息在下面。

### 建議架構

```
   政府資料源（NCDR 為主 + CWA 補充）
              │
              │  你的伺服器每 1～5 分鐘定時抓
              ▼
   ┌─────────────────────────────┐
   │  中間層（跑在你的 Oracle 機器上）  │
   │  1. 抓政府資料、解析 CAP        │
   │  2. 整理成統一乾淨的 JSON       │
   │  3. 去重、可信度評分（把 App    │
   │     階段 2 的邏輯搬上來）        │
   │  4. 存進資料庫                 │
   └─────────────────────────────┘
        │                      │
        │ App 來拉             │ 比對誰該收到
        │（前台看地圖/清單用）   │ → 發 APNs 推播
        ▼                      ▼
   App 顯示最新資料        使用者手機（背景也收得到警報）
```

**三個重點**：

1. **中間層是必要的，別讓 App 直接打政府 API。** 因為政府那堆資料格式很雜（CAP 是 XML、CWA 是 JSON、每個機關代碼不同），而且政府隨時可能改格式。如果 App 直接對接，政府一改，你全部使用者的 App 都壞掉，還得重新送審上架才能修。中間層擋在中間，政府改格式你只要改伺服器、當天就修好，App 完全不用動。**這其實就是 App 階段 2 已經做好的 `EventProvider` 那套邏輯，原封不動搬到伺服器上而已。**

2. **你已經有伺服器了，不用另外花錢。** 你的環境裡有 Oracle 鳳凰城的機器。Oracle 免費方案的機器跑這種「定時抓資料 + 發推播」綽綽有餘，不用再租主機。

3. **隱私設計（很重要，符合本專案 AGENTS.md 的規範）**：不要把使用者的住家地址上傳到伺服器。做法是——**App 只上傳「我關心哪些行政區」（例如「信義區、南港區」這種粗粒度）給伺服器，伺服器按行政區發推播；精確的「這個點在不在我畫的半徑裡」留在 App 本地比對。** 這樣你的伺服器永遠不知道任何使用者確切住在哪，只知道「有個人關心信義區」。既能推播，又保護隱私。

### 建議分兩步走（別一次做完，先讓真資料進來）

**第一步（MVP，先看到真資料，最快）**：
- 在 Oracle 上跑一個排程程式，定時抓 NCDR 的示警，整理成一個 JSON API（例如 `https://你的網域/api/events`）。
- App 端把現在的 mock provider 換成「從你這個網址拉資料」。
- 推播先**不做背景 APNs**，暫時用「App 開著的時候自己比對 + 本地通知」。
- 這一步做完，App 第一次顯示真實災害資料，而且完全不用碰 APNs 的複雜佈建。

**第二步（完整版，加背景推播）**：
- 中間層加上「比對行政區 → 發 APNs」。
- App 要多做：把裝置推播 token 和「關心的行政區」上傳伺服器。
- 這步比較複雜（APNs 憑證、token 管理），但因為第一步已經讓真資料跑起來，你可以從容做。

## 三、App 端：斷網降級與通知去重怎麼改

這兩個是你另外問的。以下是具體建議與現在的落差。

### 斷網降級（現在只有「資料更新於 X 分鐘前」）

**現況**：App 已經把事件存在本機資料庫（SwiftData），所以「斷網還看得到上次的資料」這件事其實已經有一半基礎了。缺的是「明確告訴使用者現在是離線狀態」。

**建議三個改動**：
1. **抓資料失敗時，別默默失敗**（符合你「錯誤處理要明確、不要 silent fail」的規則）。在頂部顯示一條明顯的橫幅：「⚠️ 目前無法更新，以下是離線資料（最後更新：X 前）」。現在的「X 分鐘前」是被動標示，這個是主動警示，兩者不同。
2. **成功抓到資料就整包存起來當快取**，斷網時直接顯示,並把上面那條橫幅打開。這個改動小，因為資料本來就存在本地。
3. **高風險事件的簡訊備援**（斷網也能收到最緊急的警報）——這個要簽簡訊服務商、比較大工程，**留到階段 4，現在不急**。

**落差評估**：前兩點是小改動、CP 值高，建議跟接資料一起做。第三點是獨立的大工程，之後再說。

### 通知去重（防止同一件事一直吵你）

**現況**：App 已經有 `hasNotified` 旗標——同一個事件推播過一次，就不會再推第二次。這是對的基礎。階段 2 也做了「同一件事被不同來源報成多筆時，合併成一筆」的去重。

**建議再加三層**（由簡單到複雜）：

1. **狀態升級不重複推**：一個事件從「持續確認中」升級到「官方已確認」時，會不會又推一次？建議規則是——**只在「首次達到推播門檻」時推一次**，之後狀態再怎麼變，只更新 App 內的顯示，不再發推播打擾。（這點要檢查現在 pipeline 的邏輯有沒有漏。）

2. **同區短時間洪水式事件要合併**（最有感的改善）：想像颱風天，你的「家」附近 5 分鐘內湧進 4 起淹水通報。現在會是 4 個獨立通知連環轟炸。建議改成——**同一個生活圈，短時間內（例如 5 分鐘）第 2 件以後的事件，合併成一則「你的『家』附近還有 N 起新事件」**，而不是每件一個通知。這是「通知疲勞」最主要的來源，值得做。

3. **每人每時段的推播上限**：極端情況下（大災難）替每個生活圈設一個上限，例如「10 分鐘內最多推 3 則，超過的併入下一份摘要」。這是保險絲，避免任何情況下把使用者轟到關通知。

**落差評估**：第 1 點是檢查+小修。第 2 點是這三個裡最值得做的，直接改善使用者體驗。第 3 點是保險，可以晚點做。這三點都在 App 端就能做，不用等伺服器。

## 建議動工順序（把上面全部串起來）

1. **先在 Oracle 上做 NCDR 抓取 + JSON API**（第一部分第 1 項 + 第二部分第一步）。這一步讓真資料第一次進 App。
2. **App 端把 mock 換成拉你的 API**，順手把斷網橫幅（第三部分斷網第 1、2 點）一起做。
3. **加通知去重的第 1、2 點**（狀態升級不重複、同區合併）。
4. **之後再做背景 APNs 推播**（第二部分第二步）——這步最複雜，但前面做完 App 已經有真資料可用，不趕。
5. CWA、避難所更新、簡訊備援、推播上限這些補充項，隨時可以插進來，優先度較低。

**信心等級**：資料源接取方式為**高**（已實際查證，僅少數代碼標未確認）；架構建議為**中**（方向明確且符合你現有的 Oracle 資源，但實際 APNs 佈建、Oracle 機器規格細節需動工時驗證）。
