> 目標：用「TTV 最短、價值在前、一次一決定、做中學」的原則，重新設計整條用戶流程。
> 本文是**構思**，不是實作清單；定案後才動工。

### 0.1 驗證結果（2026-07-23 實測，動工 #2）

**賭注 1：不成立（原設想的「首屏鋪 30 天事件 pin」做不到）**，依據：
- **30 天歷史不存在**：Oracle 只留滾動快照（新聞約 24h 窗、當日 56 則；官方＝目前生效 43 則）；爬蟲機 seen.json 只存 ID 不存內容。App 端新聞 TTL 也只有 12h。
- **座標精度**：新聞 0 筆有真座標——App 是用行政區 bbox 中心錨定（區級標 3km、縣級 15km 不確定度）；官方警報目前 0 筆帶 circle（只有消防署火災通報才有，屬間歇性）。
- **10 點密度實測**（24h 窗、2.5km 半徑）：9/10 個點＝0 pin。唯一例外中壢 3 則，是因為測試點剛好靠近區中心——結構性原因：pin 錨在區中心，住在區邊緣的人永遠看不到「附近」pin。門檻「首屏 ≥3」全面未達，城區也一樣。
- 塗層覆蓋還行：43 則生效警報（停水 38／強風／高溫／水庫放流）覆蓋部分行政區（板橋、三民、中壢有停水；玉里高溫）。

**§5-2 規格因此改向**：首屏價值＝「圈＋行政區警報塗層＋最近避難所」三件套；事件 pin 有就加、不撐場。帶領的「這附近發生過的」改為同行政區／同縣市 24h 清單（不是 1km 視野 pin），無資料時走避難所保底為常態。若要真 30 天歷史，需先在爬蟲端或 Oracle 加歷史累積（新工作項 S~M，待拍板）。

**賭注 1b：成立**。全國避難所資料 6,152 筆（收容所 5,947＋急救醫院 205），六個極端點（金門金城 0.4km／馬祖南竿 1.0／蘭嶼 2.8／綠島 2.0／尖石後山玉峰 1.7／信義鄉東埔 3.1km）全部遠低於 10km 門檻，**不需**行政區清單降級。
- ⚠️ 但抓到資料品質 bug：**239 筆（3.9%）座標錯置**（例：台北車站 0.2km 內出現「高雄林園汕尾國小」；新屋區 21 筆活動中心座標在馬祖外海）。保底指路上線前必須先過濾——App 已內建 TaiwanDistricts.json，載入時用行政區界檢核即可（S 級）。

## 1. 五問

1. **誰的什麼痛**：台灣家庭（尤其有長輩、小孩）在災害當下的「家人現在安全嗎」焦慮，現在靠 LINE 群組亂問。**誠實面**：平時沒有這個痛——低頻高強度，所以 (a) onboarding 要在平日證明價值，(b) 家人模塊要有平時心跳（§5 第四階），否則活不到下一次警報。
2. **成功長什麼樣**（v3 換 north star）：~~第一週發出至少一個邀請~~ → **「≥2 名成員且完成至少一次互報的家庭數」**。發送不等於加入，加入不等於用起來；量核心就量到閉環走完。過程指標：著陸→看到真實資料完成率、邀請四段漏斗、D7 留存。
3. **最窄可行切入**：單人價值（「這 App 知道我家附近的事」）是楔子；家人閉環是產品。楔子薄一點沒關係，閉環缺一格就全斷。
4. **前三賭注**：見 §0。
5. **誰會反對**：「這就是 Life360，位置分享＝監控。」回應：安心圈最小價值不需要位置分享——但要誠實面對這個定位的代價：拒絕位置常駐＝拒絕 Life360 的日常引擎，平時心跳必須另找來源（§5 第四階）。

## 2. 三版真分歧（歷史記錄，v1 產出）

- **A 減法**：方向沒錯，錯在第一張地圖是空的；改成鋪真實資料。第一步：密度查證。風險：真沒資料。
- **B 體驗劇場**：30 秒【示範】災害情境演完整閉環。第一步：寫腳本。風險：被跳過＋審查誠實性＋成本最高。
- **C 家人優先**：首屏分流、受邀路徑一鍵入圈。第一步：深連結。風險：分流懲罰 90% 自發用戶；LINE 攔 Universal Link。

## 3. Premortem（歷史記錄）

**A**：①鄉區 0 事件仍空圖；②單人價值撐不起留存，家人 hook 沒進第一 session。

## 4. 收斂（v3 修正版）

**A 為主幹**（死因可動工前驗證）；**嫁接 B** 的示範通知（要權限前先看一則【示範】）；**C 的教訓 v3 重新結算**：否決首屏分流是對的，但 v2 因此把「受邀者路徑」整個丟掉是矯枉過正——**否決 C 版 ≠ 受邁者不用設計**。折衷：著陸卡底部一行小字「我收到了邀請碼」——自發用戶根本不會注意到（不懲罰 90%），受邀者卻有直達通道。深連結維持緩議（LINE 攔截＋基礎設施不存在），先用 8 碼收數據。

## 5. 合成後的新流程藍圖

> 工作量級距：**S**＝文案/接線（天內）、**M**＝功能開發（數天）、**L**＝獨立子專案（先出設計稿）。

### 第一階：證明「它知道我家」（0–45 秒）——楔子
1. **[S/已存在]** 乾淨地圖著陸＋點擊授權定位。**（v3 新增）**著陸卡底部小字連結「**我收到了邀請碼**」→ 走受邀精簡流程（見 §5-7）。
2. **[M]** 授權後：預設 1 公里圈＋地圖鋪真實資料。動工前要寫規格：查詢半徑（＝首屏視野）、顯示上限（事件 ≤10 pin）、歷史事件視覺區分、圖層優先序。
3. **[S]** 脈動帶領指真東西：守護範圍 →（有近事件）這附近發生過的 →（保底）最近避難所。

### 第二階：情境式要通知權限（45–90 秒）
4. **[S~M]** 帶領結束或首次點開事件後，中央卡「圈內有新狀況時，要通知你嗎？」＋「先看看警報長什麼樣」發【示範】通知 → 才跳系統框。拒絕不糾纏。

### 第三階：家人閉環（v3 全面補強——這才是核心，資源配置從本版起說到做到）

**5a [S]** 家人空狀態改情境卡：「**災害來的時候，一個人知道不夠。**」＋「邀請家人」。

**5b [S]（v3 新增）情境觸發邀請**：第一次真實警報後按「回報我平安」、但家庭圈沒有其他人時——「你的回報已記錄，但還沒有家人會看到。邀請家人，讓他們安心。」動機最高的時刻，轉換率預期是空狀態卡的數倍（估計，漏斗驗證）。

**6 [L——獨立設計稿]** 註冊時序：Apple 登入只在建立/加入家庭圈時出現；匿名起步、入圈時綁定。設計稿必解：`credentialAlreadyInUse` 資料合併、既有用戶遷移、登入 gate 盤點、孤兒帳號清理。

**7 [S~M]（v3 重寫）受邀者專用通道**——受邀者的 onboarding 理由就是邀請者本人，不需要脈動帶領：
   - 入口：著陸卡底部「我收到了邀請碼」（§5-1）。
   - 精簡流程：輸碼（大字格子輸入框）→ 定位授權 → **第一眼直接看到邀請者的圈**（受邀者的 aha：「我看得到家人」）。
   - 阿嬤測試：這條路徑必須讓長輩在 LINE 收到訊息後，被訊息裡的步驟一步步牽著走完，走廊測試指定含此情境。

**7b [S]（v3 新增）邀請訊息規格**——漏斗的真正頂端，當功能寫，不讓用戶自己想怎麼轉述：
   - 內容：App Store 連結＋8 碼＋**以邀請者名義的一句理由**（例：「爸爸想在颱風天知道你平安」——名字用邀請者的身分/暱稱自動帶入）。
   - 由 ShareLink 產生，複製即整段可貼 LINE。

**7c [S~M]（v3 新增）邀請者慶祝閉環**——峰終定律裡最該做峰的地方：
   - 家人輸碼入圈成功 → 邀請者手機**立刻**收到推播「**媽媽加入了你的安心圈**」→ 點開地圖上多了她的圈。
   - 這是全產品最有情感重量的一則通知，也是邀請第二個人的動力來源。
   - 技術：入圈寫入 Firestore 時觸發（FCM 現成；細節與第 6 步設計稿同批確認）。

**8 [S]** 選家庭身分（六方塊）接回「入圈成功」瞬間——身分第一次有意義；7c 的通知因此能顯示「媽媽」而不是帳號暱稱。

### 第四階：平時心跳＝**週報家庭摘要**（2026-07-21 使用者拍板）

拍板理由：①颱風儀式的觸發條件是「有災害」，定義上答不了「沒事的日子靠什麼活著」（11 月裝機到隔年 7 月＝8 個月零心跳）；②週報每週出數據、三週可迭代，颱風一年三五個樣本無法學習——**能學習的功能優先於不能學習的**；③digest 機制已有基礎，S~M 就能驗證「規律的『沒事』內容能維持存活感」這個假設。

**三條設計護欄（寫進規格才動工）**：
1. **絕不動用警報的信任額度**：週報無聲或系統預設音、不用紅色、標題永遠不出現「警報」「事件」字眼。警報通知的可信度是命根子。
2. **永遠有內容，內容＝承諾的兌現**：「你家 3 個圈本週平安」就是「我在替你看著」的每週兌現；附近有已結束事件就列，沒有就報平安＋一條季節防災提示。**不因為沒事而跳過發送**——跳過一次，儀式就斷。
3. **護欄指標優先於成功指標**：成功看週報開啟率＋digest 兩組 D30 留存差；**護欄看「收到週報用戶的通知關閉率」**——相對照組上升就立刻降頻或砍，不商量。護欄埋點併入第一批。

**颱風儀式不是輸了，是歸錯類**（拍板一併決定）：移出心跳槽、歸入**核心警報迴圈 backlog**——颱風海警發布時 App 本來就推警報（既有管線），只需在該警報與事件詳情裡把「詢問家人是否平安」升到顯眼位置＋一句「颱風接近中，先跟家人確認一下」。S 級、直接驅動 north star（互報），第一個颱風來之前上線。

### 貫穿全程的三條紀律
- **漏斗埋點**：機制現成、事件目前只有 3 個；第一批動工。v3 清單：著陸→點擊→定位允許/拒絕→看到資料→通知允許/拒絕→**邀請發出→對方安裝→對方入圈→首次互報**（後四段是賭注 3 的斷點定位器）。
- **清 iCloud 殘留文案**（信任破口）。
- **走廊測試**：2–3 個生人＋一位長輩，**必含「LINE 收到邀請訊息→入圈」的受邀者全程**。
